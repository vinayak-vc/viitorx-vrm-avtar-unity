# Full-Body Tracking — Deep Technical Audit (2026-09-07)

**Scope:** OAK-D → Python sidecar (RTMW3D + measured depth) → UDP → Unity (`OakDUdpPoseProvider` → Kalidokit normalized control-rig driver) → VRM avatar.
**Method:** evidence-first, code + runtime. Runtime evidence = the committed 3-stage pipeline logs (`python-sidecar~/pipeline_logs/{sender,recv,model}_log.jsonl`), captured with `run_capture.bat` (`--min-cutoff 0.5 --beta 0.4 --depth-min-cutoff 0.3 --depth-beta 0.1 --max-hold-frames 8`, flatten-trunk OFF, mirror OFF).
**Rule of the audit:** no evidence = no claim. Class names are not proof; data flow is.

---

## 0. Executive summary

The shipping path (confirmed in `Scenes/Bootstrap.unity`: `useOakUdpTracking=1`, `useKalidokitBody=1`, `useIkDriver=0`) is a **rotation-based** pipeline: the sidecar produces smoothed metric landmarks, Unity converts them, the Kalidokit port solves **per-bone Euler rotations**, and those drive UniVRM's **normalized control rig**. Because bones receive rotations on a fixed-length rig, **bone stretch/squash is architecturally impossible** — the brief's central squash hypothesis does not occur here (VERIFIED).

The system is a **well-instrumented, heavily-tuned prototype**, not production-robust. Its real weaknesses are:

1. **Confidence is gated only at the sidecar; it never influences the Unity solve.** An invalid/zeroed body joint drives a limb rotation from the origin → limb collapse during occlusion (the one place the "raw landmarks must never drive the avatar" rule is genuinely violated — *invalid* data drives the avatar).
2. **Metric spikes survive to the limbs.** Runtime: post-smoothing left-wrist frame-to-frame Δ **max 0.86 m**, palm quaternion Δ **max 180°**, while shoulders/hips are rock-stable (~2 mm). The One-Euro is velocity-adaptive and the `--max-jump 1.5 m` gate sits *above* the 0.8 m spikes, so limb spikes leak; trunk is stable because it is flattened/heavily damped.
3. **No per-joint temporal tracker** (no velocity, no prediction, no TRACKED/PREDICTED/LOST state). Recovery = a bounded 8-frame hold in the sidecar (limbs only) + fixed slerp in Unity.
4. **No Unity pose buffer / timestamp interpolation.** `seq` + `t` are sent and received but used only for log alignment; Unity applies latest-wins with a fixed per-frame slerp.

Depth acquisition, the rotation-retarget choice, the threading model, and the diagnostics are **correct and should not be changed**.

**Overall architecture score: 124 / 210 (~59%). Production readiness: PROTOTYPE.**

## 5. Detailed findings (evidence-first)

### FINDING #1 — Confidence never reaches the solve
- **Category:** Confidence Handling · **Severity:** CRITICAL · **Status:** INCORRECT
- **Finding:** Per-joint confidence is used only to gate emission in the sidecar; the Unity Kalidokit solve consumes bare positions, so an invalid joint drives a real bone rotation.
- **Evidence:** `Runtime/Retargeting/Kalidokit/KalidokitPoseSolver.cs:35` `Solve(Vector3[] lm)` — no confidence parameter. `Runtime/Retargeting/KalidokitControlRigDriver.cs:220` reads `frame.GetLandmark(i).Position` only; the only validity guard is the **Hand bone** (`:306-309`), not the fore/upper-arm or legs. Sidecar leaves sub-threshold joints as `[0,0,0,0]` (`wholebody_udp_sender.py:83-94`).
- **Data flow:** sidecar emit-gate (drops to zero) → UDP → `ParseInto` (zero → `converter.ToUnity` → (0,0,0)) → `KalidokitPoseSolver` (elbow→(0,0,0) direction) → `ApplyBone` slerp 0.5 → forearm swings toward hip origin.
- **Observed:** A lost wrist yields a forearm that aims at the pelvis. **Expected (V2):** low-confidence joint is down-weighted/held, not applied. **Gap:** confidence is “computed but functionally unused” past the sidecar gate.
- **Impact:** limb collapse/twitch during any occlusion that outlasts the 8-frame hold. **Confidence:** HIGH (code path explicit).
- **Fix:** thread each landmark’s confidence into `Apply`; when a limb’s driving joints are sub-threshold, hold the previous applied rotation (or blend by confidence) instead of applying the origin-aimed solve.

### FINDING #2 — Missing-joint recovery is a bounded hold, no state machine
- **Category:** Missing-Joint / Occlusion · **Severity:** HIGH · **Status:** PARTIAL
- **Evidence:** `python-sidecar~/smoothing.py:101-103` holds a limb’s last smoothed value for `max_hold=8` frames then resets to invalid; `wholebody_udp_sender.py:73-99` then emits zeros / halved-confidence fallback. No TRACKED/PREDICTED/LOST anywhere; `Runtime/Core/Models/PoseFrame.cs` stores no per-joint state/velocity/last-valid.
- **Observed:** ≤8-frame dropouts bridge; longer → joint zeros → F-01 collapse. Re-acquire after a long loss snaps (no blend). **Expected:** PREDICT short gaps, HOLD/CONSTRAIN long gaps, smooth re-acquire. **Gap:** no prediction, no re-acquire blend, no explicit states.
- **Impact:** occlusion instability + teleport on reappearance. **Confidence:** HIGH.

### FINDING #3 — Limb metric spikes survive to the avatar
- **Category:** Temporal Tracking / Jitter · **Severity:** HIGH · **Status:** INCORRECT
- **Evidence (RUNTIME):** `recv_log.jsonl` (post full sidecar smoothing) — L-wrist frame-to-frame Δ mean 0.023 m, p95 0.063 m, **max 0.857 m**; R-wrist max 0.787 m; L-elbow max 0.471 m; palm Δ **max 180°**. Shoulders/hips: mean 4.5 mm / 1.2 mm (stable). **CODE:** `smoothing.py:112-124` rate-limit uses `max_jump=1.5 m` (default `run_capture.bat` — above the 0.86 m spikes); One-Euro is velocity-adaptive (`smoothing.py:47-56`) so a fast step opens the cutoff and passes.
- **Observed:** trunk stable, limbs spike. **Gap:** no robust (median) limb filter; the outlier gate is set looser than the observed spikes.
- **Impact:** forearm/hand twitch reaching the solve (softened only by `ApplyBone` slerp 0.5). **Confidence:** HIGH (runtime + code).

### FINDING #4 — Legs are the least-protected chain
- **Category:** Temporal Tracking · **Severity:** HIGH · **Status:** PARTIAL
- **Evidence:** `wholebody_udp_sender.py:221` — `limb_idx = {5,6,7,8,9,10,11,12} ∪ range(91,133)`; the comment states knees/ankles (13-16) are deliberately excluded so an occluded lower body drops. Consequence: legs get only the default image-plane One-Euro (no heavy depth cutoff, no hold-on-dropout).
- **Impact:** leg-depth jitter and single-frame leg collapse are more likely than arms; combined with F-01 (no leg confidence gate in the solve) a bad knee swings the whole leg. **Confidence:** HIGH.

### FINDING #5 — No Unity pose buffer / timestamp interpolation
- **Category:** Networking / Interpolation · **Severity:** MEDIUM · **Status:** MISSING
- **Evidence:** `OakDUdpPoseProvider.cs:205-219` swaps to the newest frame (latest-wins); `seq` parsed at `:272` and `t` sent at `wholebody_udp_sender.py:310` are used only for log alignment. No buffer of N poses, no interpolation by timestamp. Mitigation: `ApplyBone` slerp 0.5 + `ApplyRootPosition` exp-Lerp give a crude move-toward-latest.
- **Impact:** render(~60)/datagram(~30) mismatch → the same pose re-applied ~20× (model_log 78 027 vs recv 3 947) and micro-stutter on rate changes. **Confidence:** HIGH.

## 6. Jitter forensics (the "PROVE IT" traces)

**PROBLEM: left-wrist jitter / forearm twitch**
- TRIGGER: fast hand move or a partial-occlusion frame at ~2.5 m.
- INPUT: RTMW3D wrist pixel + a depth sample straddling the hand/background edge.
- T1 `oak_depth.sample_depth_mm:67` — 5×5/p30 helps but a thin fast hand still lands a wrong sample some frames.
- T2 `smoothing.KeypointSmoother.filter:112-124` — Δ 0.86 m < `max_jump 1.5` → **not rate-limited**; velocity-adaptive One-Euro opens → spike passes.
- T3 `KalidokitArmSolver` (via `KalidokitPoseSolver.Solve`) — wrong wrist → wrong forearm Euler.
- FAILURE POINT: no confidence gate + a too-loose outlier gate on limb Z.
- VISIBLE: forearm jerks ~half-way (slerp 0.5) then back → shimmer.
- MISSING CONTROL: robust/median limb filter or confidence-weighted One-Euro (V2 Temporal Tracking).

**PROBLEM: wrist "helicopter"/flip** — palm Δ max 180° (recv_log). Mitigated by `OakDUdpPoseProvider.cs:359-383` (slerp 0.15 + 15°/frame cap) and roll-free `FromToRotation` (`KalidokitControlRigDriver.cs:438`). Residual, not eliminated.

## 7. Avatar "squash / deformation" forensics — the brief's scenario

**Scenario:** knee detected 25-40 cm wrong for ≥1 frame; or Frame N hip→knee 0.42 m, Frame N+1 0.15 m.

- Detector emits wrong knee px (`rtmw3d_pose.infer`), conf may stay > 0.3 → passes emit.
- Depth back-projects the wrong px → wrong 3D knee (`oak_depth.backproject`).
- Smoothing: **knees are excluded from depth-smoothing/hold** (`wholebody_udp_sender.py:221`), only image-plane One-Euro applies; a 25-40 cm step < `max_jump 1.5` → passes.
- Reconstruction: `KalidokitPoseSolver.CalcLegs:90-110` computes thigh/shin **rotations** from spherical coords of hip→knee→ankle; `RigUpperLeg:112-116` **clamps** the angles to anatomical ranges.
- Drive: `ApplyBone` slerp 0.5 → leg swings ~half-way to the wrong (clamped) angle, back next frame.

**Result: the leg JERKS to a wrong angle — it does NOT squash.** The hip→knee distance changing to 0.15 m never shortens the femur, because the knee **position is only used to derive a rotation**; the rendered femur length is the VRM rig's, applied by `Vrm10 Runtime.Process`. **Where it *should* have been rejected but wasn't:** a per-joint velocity/anatomical outlier reject or confidence gate on the knee before the solve (F-01/F-04). The angle clamp (`RigUpperLeg`) prevents an *impossible* pose but not a *wrong* one.

**Conclusion (VERIFIED):** avatar squashing/stretching is **not reproducible** in the current architecture; the correct symptom to chase is limb *mis-rotation/jerk*, driven by F-01 + F-03 + F-04.

## 8. Missing-joint / occlusion forensics (left wrist gone 3-5 frames)

- Frames 1-5: sidecar `smoothing.filter` holds the last smoothed wrist (limb ∈ `limb_idx`, `max_hold=8`) → wrist streams last-good, arm steady. **Good.**
- Frames 6-8: still held (bound not yet hit).
- Frame 9+ (if still gone): hold resets → `emit` sees conf<0.3 → wrist slot `[0,0,0,0]` → Unity (0,0,0) → forearm aims at hip origin (F-01) → **collapse**. On return: no re-acquire blend → snaps to the new solve, softened only by slerp 0.5.
- **Dangerous cases:** any occlusion > ~8 frames (arms crossed, turning sideways, hand behind torso), and legs at any dropout (excluded from hold). Elbow/knee loss is worse than wrist because there is no downstream bone-gate for them (only the Hand bone is gated).

## 9. Depth / RGB fusion audit — a verified STRENGTH

- Pipeline builds RGB-aligned stereo depth (`oak_depth.build_rgbd_pipeline:41` `setDepthAlign(CAM_A)`), reads real intrinsics scaled to the depth frame (`read_rgb_intrinsics:56`), samples a **5×5 window at the 30th percentile** (nearer surface, correct on person/background edges — `sample_depth_mm:67-88`), rejects holes (`min_valid=6`), and back-projects through the pinhole model (`backproject:91-116`). Limb depth is damped harder than the image plane (`smoothing.py:83-88`). Depth genuinely **influences** the 3D estimate and validity — real fusion, not decorative. **Do not change.**
- One weakness: RGB/depth are paired by queue order, not timestamp (F-09).

## 15. Minimum Viable Stability Patch
Two focused changes, no architecture change:
1. **P0-1** confidence-hold on limbs in the driver (stops occlusion collapse).
2. **P0-2** include legs in depth-smoothing/hold + tighten limb outlier gate (stops leg/arm spikes).
Both live in already-present code paths (`smoothing.py` `limb_idx`, `KalidokitControlRigDriver.Apply`). Expected: eliminates the two most visible failures (occlusion limb-collapse, limb twitch) while keeping the current stable trunk/root behavior.

## 18. Final verdict
1. **Suitable for production?** Architecture yes (rotation retarget + measured depth + strong diagnostics is the right backbone); current *implementation* no — it lacks confidence-in-the-loop and per-joint recovery.

3. **Top 5 reasons it feels unusable:** (1) occlusion limb-collapse (F-01), (2) limb/leg spikes (F-03/F-04), (3) no prediction/re-acquire → teleport (F-02), (4) no interpolation buffer → stutter (F-05), (5) wrist residual noise (F-07).

5. **Do not change:** depth fusion, rotation-based control-rig retarget, threading, single-owner smoothing decision, diagnostics.
6. **Minimum stable prototype:** the two-change MVP patch (§15).
7. **Production quality also needs:** state-machine recovery, interpolation buffer, ground/foot lock, latency+loss telemetry, facing disambiguation, automated tests.
