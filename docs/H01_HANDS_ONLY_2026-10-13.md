# H-01 - Hands only: find, track and read hands with no body in the picture (2026-10-13)

Status: **BUILT, TESTED (207 assertions, 25 of 25 mutants caught), RUN END TO END ON A RECORDED CLIP. NOT RUN ON A LIVE WEBCAM OR A PHONE.**
Decision: [`decisions.md`](decisions.md) **ADR-099**. Tasks: [`tasks.md`](tasks.md) H-01. Sidecar repo: `python-sidecar~/` (modules at its root, entry in `tools/hands/`).
Next: the Unity receiver, then **H-02: face only with 52 blendshapes** (same pattern, a second port).

---

## 1. The question this answers

The whole-body sidecar cannot track a hand that appears without a body. RTMW3D reads hands out of a crop it cuts around a detected PERSON; with no person
there is no crop, `video_udp_sender.py` drops the frame, and the OAK sender sends nothing ("no body, no send, by design"). A project that only needs hands
(a desk camera, a kiosk, a gesture interface) therefore could not use it.

H-01 adds a separate hands pipeline to the same repository. It needs no body, no person detector and no RTMW3D.

## 2. What it is

```
camera:N | LAN camera link | rtsp/http stream | file        (the video sender's source handling, reused)
  -> orient (--rotate / --flip)
  -> HandTracker (hand_tracking.py), per frame:
       tracked hand      -> landmark net on a crop PREDICTED from last frame's landmarks   (no palm detector)
       room for another  -> palm detector (rate-limited when a hand is already tracked)    -> landmark net
     the results are matched to the tracks by motion (optimal assignment), duplicates dropped, ids kept
  -> per hand: One-Euro smoothing, 3D placement (hand_geometry.py), finger curls + gesture (hand_gestures.py)
  -> ONE JSON datagram per frame to 127.0.0.1:8901                                           (hand_wire.py)
```

The networks are MediaPipe's palm detector (192x192) and hand-landmark network (224x224; 21 landmarks, 21 metric world landmarks, handedness, confidence),
as the OpenCV Zoo ONNX conversions (Apache-2.0, 3.9 MB + 4.1 MB), run on the existing `onnxruntime-directml`. **No new pip package**: the venv is untouched.
`pip install mediapipe` was rejected because it would pull `opencv-contrib-python` next to the `opencv-python` every other sender uses.

## 3. What was built

| File | Role |

| `tools/hands/hands_udp_sender.py` | the entry point (`--show` is the demo) |
| `tools/hands/hands_udp_receiver.py` | reference receiver; `--view` draws the hands FROM THE DATAGRAM ALONE |
| `tools/hands/hands_eval.py` | measures the pipeline on a clip (the numbers below) |

## 4. How to run it

```
python-sidecar~/.venv/Scripts/python.exe tools/model/fetch_hand_models.py          # once; writes models/*.onnx (git-ignored)
python-sidecar~/scripts/run_hands_demo.bat                                          # webcam 0 + the demo window
.venv/Scripts/python.exe tools/hands/hands_udp_sender.py --video camera:0 --flip --show
.venv/Scripts/python.exe tools/hands/hands_udp_sender.py --video "http://192.168.1.5:3000/viewer?room=room-abc" --show     # LAN camera; set CAMERA_PIN first
.venv/Scripts/python.exe tools/hands/hands_udp_receiver.py --view                   # in a second terminal: what a client sees
```

Every flag has a help line (`--help`). The ones that matter: `--hfov` (the camera's field of view, **assumed**, see 6), `--hand-scale`, `--max-hands`,
`--flip` (selfie mirror), `--rotate`, `--sides`.

## 5. The wire (ADR-099; the full field list is the docstring of `hand_wire.py`)

`{ver:1, kind:"hands", sid, seq, t, lat, src, img:[w,h], fpx, mir, n, hands:[{id, side, hd, conf, st, lm[21x3], wl[21x3], pos[3], why, fing[5], ext[5], pinch, ges}]}`

* `lm` = normalised image coordinates (x/w, y/h, z/w); `wl` = metres, hand-centred (x right, y DOWN, z away); `pos` = the hand's centre in camera space
  (X right, Y down, Z forward), metres - **absent** when the 3D fit was refused, with `why`.
* A frame with no hand is `n = 0`, so a receiver tells "no hand" from "no sender". A hand that is not there is not in the list; nothing is predicted past a
  `HELD` frame or two.
* Port **8901**, not the body sender's 8899: the VRM mirror, every scene and `OakDUdpPoseProvider` are untouched and unaware.
* `n` never exceeds `--max-hands` (a HELD hand gives way to a tracked one).

## 6. Measured

Measured on `Assets/Games/video/video.webm` (a woman dancing, 720x1280, 435 frames), cropped to the upper body and upscaled 1.4x
(`hands_eval.py --crop 0 150 720 850 --upscale 1.4`), RTX 3060, DirectML. **This is a hard clip** (hands a few dozen pixels wide, motion blur, both hands
moving), not a webcam at a desk.

| | |
|---|---|
| frames with at least one hand | 431 / 435 (99%) |
| cost per frame (tracker, decode excluded) | 6.7 ms mean, 16.5 ms p95 on DirectML; 6.8 / 15.4 ms on CPU |
| palm detector | 5.0 ms (DirectML), 8.4 ms (CPU), 126 calls in 435 frames |
| landmark network | 2.5 ms (DirectML), 2.0 ms (CPU) |
| end to end through the sender and the receiver | 30 msg/s from a real-time clip, `bad=0`, `seq_gaps=0` |
| identity | 94 losses; 78 re-found with the SAME id, 16 as new ids; 22 ids over 435 frames and two hands |
| 3D fit | converged on all 99 real detections (right sign convention, residual 5% of the hand's extent on average, max 11.6%) |
| the network's metric scale | wrist to middle knuckle median 0.085 m (a real adult hand is ~0.09-0.10): the network's hands read slightly SMALL, so depth reads slightly near |

The synthetic tests pin: the ROI warp lands a known point where the mapping says (test bound 1.2% of the crop) for turns of 0, 30, 90, 180 and -60 degrees; the depth fit recovers a known
position to 0.000% for a flat hand and within 3.1% (0.6 m) / 5.6% (0.25 m) for a hand tilted 60 degrees - the weak-perspective error, which grows as the hand nears
the lens; a hand 20% bigger than the network's average reads 20% too near and `--hand-scale 1.2` removes it; a finger swept closed and open flips its state exactly twice.

**Mutation check.** 25 deliberate bugs (a flipped rotation, a dropped half pixel, an inverted depth, a removed gate, a reused id, a removed version check, ...)
were injected one at a time; every one failed a named test. Two survived the first round (the side tie-break when two lost hands return, and the cap on how
many hands are reported) and each got the test that kills it.

## 7. NOT TESTED - read this before relying on it

* **A live webcam or a phone / LAN camera.** The live reader (`LatestFrameReader`, `LanCameraReader`) is the video sender's existing, separately tested code and was
  reused, not re-run here. Nothing in H-01 has seen a camera frame.
* **Absolute depth against a ruler.** `pos.Z` is an estimate from the hand's apparent size and an ASSUMED field of view (`--hfov`, default 60 degrees, the camera
  does not report it). Every metre scales with that guess and with the user's hand size (`--hand-scale`). The fit's internal consistency is tested; its accuracy is
  not. Measure it: hold a hand at 0.3 / 0.5 / 0.8 m from the lens and compare `pos[2]`.
* **Left / right.** MediaPipe's label assumes a mirrored picture. `--sides auto` flips the label when the picture is NOT mirrored. This is from the documentation, not
  checked against a known hand: raise your right hand with `--show` and read the letter; `--sides model|swapped` overrides.
* **Gesture thresholds** (`hand_gestures.py`) are anatomical constants checked against synthetic hands of known joint angles. Whether they hold for real hands is
  unmeasured; the gesture is forced to NONE below landmark confidence 0.7 because a blurred hand gets landmarks that are a guess.
* **Smoothing constants** (One-Euro) are starting values. The only jitter figure is on a dancing clip, where movement is mostly real (14% less frame-to-frame
  landmark motion smoothed vs raw); a still hand was not measured, so no jitter claim is made.
* **Three or more hands**, a hand under strong backlight or in a glove, two people's hands in one frame.

## 8. Known limits (do not re-discover)

* **Crossing hands.** When two hands cross, their predicted crops overlap and can both lock onto one hand (MediaPipe's own failure). The tracker never reports a hand
  where there is none and never more than `--max-hands`, finds both again once they part, and re-adopts an id by position and side - but the ids may swap or be
  re-issued across a crossing. Tested as an invariant, not as identity (`test_hand_tracking.py`).
* **Small hands.** The palm detector sees a 192 px letterboxed picture: a hand narrower than ~5% of a 1280 px frame is below it. A full-body clip needs a crop (`hands_eval.py --crop`).
* **Ids churn on blur.** On the dancing clip 16 of 94 losses came back as new ids. A hand held still keeps its id for as long as it is tracked.
* **The entry point is in `tools/hands/`, not at the sidecar root,** because it reuses the video sender's source handling and `tools/` is not shipped in a Unity
  build (`SidecarBuildPostprocessor` copies `root/*.py`). The six `hand_*.py` modules ARE at the root and import nothing from `tools/`. To ship the hands sender in a
  build, extract `video_udp_sender`'s camera / stream / LAN readers into a root module first.
* `fetch_hand_models.py` uses the Hugging Face mirror of the OpenCV Zoo files: GitHub's LFS download host was reset by this network.
