## 1. What the user asked for

"Start face only with 52 blendshapes", after hands: webcam and LAN camera (url) as sources, a new sender in this repo, licensing "carry what is current".

**What "52" means, said plainly.** MediaPipe's blendshape network emits 52 scores. Index 0 is `_neutral`, MediaPipe's own extra channel (how neutral the face is);
indexes 1-51 are the 51 ARKit-compatible blendshapes (`browDownLeft` ... `noseSneerRight`). **There is no `tongueOut`.** ARKit's own list has 52 including tongueOut, so a
consumer that expects ARKit's 52 by index will be off: use the names (`face_wire.BLENDSHAPE_NAMES`, `bsv: 1`).

## 2. What it is

```
camera:N | LAN camera link | rtsp/http stream | file        (the same sources as the hands; tools/video/vision_sender.py)
  -> crop / rotate / flip
  -> FaceTracker (face_tracking.py), per frame:
       tracked face     -> mesh network on a crop PREDICTED from last frame's landmarks   (no detector)
       room for another -> BlazeFace detector (rate-limited when a face is already tracked)   -> mesh network
  -> per face: 478 landmarks (smoothed), 52 blendshapes (read from the RAW landmarks, smoothed per channel, clamped),
               head pose + 3D position (from the smoothed landmarks)
  -> ONE JSON datagram per frame to 127.0.0.1:8902                                              (face_wire.py)
```

Three networks, community ONNX conversions of the TFLite models in Google's `face_landmarker.task` (Apache-2.0): a face detector (BlazeFace short range, 0.4 MB), the face mesh
(478 landmarks incl. iris, 4.9 MB) and the blendshape network (an MLP-Mixer over 146 of the landmarks, 1.1 MB). They run on the existing `onnxruntime-directml`: **no new pip package.**

## 4. How to run it

```

python-sidecar~/scripts/run_face_demo.bat                                              # webcam 0 + the demo window
.venv/Scripts/python.exe tools/face/face_udp_sender.py --video camera:0 --flip --show
.venv/Scripts/python.exe tools/face/face_udp_sender.py --video "http://192.168.1.5:3000/viewer?room=room-abc" --show     # LAN camera; set CAMERA_PIN first
.venv/Scripts/python.exe tools/face/face_udp_receiver.py --view                        # second terminal: what a client sees
```

Switches that matter: `--hfov` (assumed), `--face-scale`, `--max-faces`, `--flip`, `--rotate`, `--crop X0 Y0 X1 Y1`, `--no-blendshapes` (landmarks and pose only, cheaper),
`--landmarks full|mesh|none` (the datagram is ~11 KB with all 478, ~0.6 KB with none).

## 5. The wire (ADR-100; the full field list is the docstring of `face_wire.py`)

`{ver:1, kind:"face", sid, seq, t, lat, src, img:[w,h], fpx, mir, bsv, n, faces:[{id, conf, st, bs[52], lm[478x3], pos[3], why, yaw, pitch, roll, rot[9], pose}]}`

* `bs` = blendshape scores in `BLENDSHAPE_NAMES` order; `lm` = normalised image landmarks (x/w, y/h, z/w); `pos` = the point between the eyes in camera space, metres,
  **absent** with a `why` when the 3D fit is refused; `yaw/pitch/roll` degrees + `rot` the 3x3 behind them.
* A frame with no face is `n = 0`. A face that is not there is not in the list; nothing is predicted past a `HELD` frame or two. `n` never exceeds `--max-faces`.
* Port **8902** (hands 8901, body 8899): nothing that reads those is affected.
* "Left" and "Right" in a blendshape name are the SUBJECT's, as in ARKit.

## 6. Measured

Measured on `Assets/Games/video/video.webm` (a woman, 720x1280, 435 frames) **cropped to the face** (`--crop 110 60 610 560`), RTX 3060. A close, frontal, mostly still face
(the easy case for a webcam); not a stress test.

| | |
|---|---|
| frames with a face | 435 / 435, one id for the whole clip, the detector ran once |
| cost per frame after the first (decode excluded) | CPU: 7.9 ms unsmoothed, 8.2 ms smoothed. DirectML: 8.5 / 10.3 ms |
| the stages | mesh 6.3 ms, blendshapes 1.1 ms (CPU); the detector only on the first frame |
| DirectML first frame | 252 ms (graph compilation) against 13 ms on CPU. CPU is as fast as DirectML for these small networks and has no warm-up; `--provider cpu` is the safe choice when the GPU is busy with a game |
| smoothing cost | 0.3 ms a frame after the filter was vectorised (it was ~3 ms: 1,486 scalar filters in a Python loop) |
| end to end, sender -> UDP -> receiver | 29-30 msg/s from a real-time clip, `bad=0`, `seq_gaps=0` |
| frame-to-frame movement, smoothed vs raw | landmarks 0.00912 vs 0.01108 of the frame width; blendshapes 0.00635 vs 0.01828 per channel (a 65% cut in expression flicker) |
| the real networks on real footage | the face is found and meshed in 22/22 sampled frames (10 inspected by eye: the mesh sits on the face); a closed mouth reads jawOpen < 0.2; a next-frame crop predicted from landmarks re-reads the same face (mean landmark shift < 1.5 px) |

The synthetic tests pin: every angle is read back **exactly** over +-60 degrees (yaw, pitch, roll alone) and the 3x3 rotation exactly for combined rotations; the position is within 3%
over 0.3-2.0 m (the perspective across the face's own depth); a face 20% wider than assumed reads 20% too near and `--face-scale` removes it; the blendshape network is handed the
RAW landmarks even with smoothing on; a 0 -> 1 blink step reaches > 0.75 in 3 frames.

**Mutation check.** 42 deliberate bugs across the hand, face, shared-geometry and filter code (a reversed eye line, an ROI scale of 1.0, an unweighted NMS, a blendshape input of y,z,
blendshapes read from the smoothed landmarks, a flipped head frame, a reused id, a removed version check, ...) were injected one at a time: every one fails a named test. Three survived the
first round (blendshapes read from the SMOOTHED landmarks, the detector's rate limit, the tiny-crop rejection) and each got the test that kills it.

## 7. NOT TESTED - read this before relying on it

* **A live webcam, a phone, a LAN camera.** The live readers are the video sender's existing, separately tested code, reused. Nothing in H-02 has seen a camera frame.
* **The community conversion against Google's.** The three ONNX files were converted by a third party, who reports parity with Python mediapipe on four test images (landmarks <= 0.6 px,
  blendshapes <= 0.015). That was **not reproduced here** (mediapipe was deliberately not installed); the evidence here is that the pipeline finds, meshes and scores a real face sensibly.
  To prove parity: build a throwaway venv with `mediapipe` and `face_landmarker.task`, run both on the same frames, compare `bs` and `lm`.
* **The expressions themselves.** The clip has no blink, wide-open mouth or brow raise to check each channel against. Raise your eyebrows, blink, open your mouth with `--show` on and watch
  `browInnerUp`, `eyeBlinkLeft/Right`, `jawOpen` (the panel lists the strongest); check which of `...Left` / `...Right` moves when you close YOUR left eye.
* **Head pose.** A geometric estimate from four landmarks (eye corners, forehead, chin), NOT MediaPipe's facial transformation matrix and not compared with it. A real face's neutral pose has a
  pitch offset of a few degrees that is uncalibrated. The signs are pinned by tests (`face_geometry.py`), the values against a real head are not.
* **Position (`pos`).** An estimate from the eye-corner distance against an assumed 0.09 m and an ASSUMED field of view (`--hfov`, default 60 degrees). Not measured against a ruler.
* **Smoothing constants** are starting values. The blendshape filter was checked for a step (blink) and a resting channel in tests, not against a live face.
* **Several faces, glasses, strong rotation beyond ~60 degrees, a face partly out of the frame.**

## 8. Known limits (do not re-discover)

* **The detector is SHORT RANGE.** BlazeFace sees a 128 px letterboxed picture and is built for a face that fills a good part of it. On the full 720x1280 frame, where the face is ~125 px wide in a 1280 px tall frame (about 10% of the 128 px letterbox the detector sees), it finds NONE
  (a test asserts it); cropped to the face it finds it at 0.97. A webcam at a desk or a phone held up is fine; a person across a room is not. `--crop` stands in for a closer camera.
* **Playing a FILE with a slow first frame used to lose the face.** DirectML's 250 ms warm-up made the file pacer drop frames to catch up and the picture jumped. The pacer now restarts its clock after
  the first frame (`vision_sender.run`). Live cameras were never affected.
* **Ids on a hard clip** (hands, H-01) churn; on this face clip they did not. Several faces were not measured.
* **Left / right under `--flip`.** The picture is mirrored before the model, so "Left" is the subject's real left in the mirror view and `pos.X` / `yaw` / `roll` are mirrored; `mir: 1` says so.
* **The entry point is in `tools/face/`**, because it reuses the video sender's source handling and `tools/` is not shipped in a Unity build. The `face_*.py` modules, `roi_geometry.py` and
  `landmark_filters.py` are at the root and import nothing from `tools/`.
* **Model provenance.** Community ONNX files on Hugging Face, fetched by size and SHA-256 (the hashes pin THESE files, they do not vouch for them). `ThirdPartyNotices.txt` entry 14 says so.
