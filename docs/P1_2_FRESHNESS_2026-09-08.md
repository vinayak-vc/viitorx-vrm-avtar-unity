## 1. Current architecture (as audited)

```
OAK-D device                                       HOST
─────────────                                      ────────────────────────────────
ColorCamera 30fps ─► XLinkOut "rgb"   ──XLink──►   q_rgb   maxSize=4 blocking=False
StereoDepth  30fps ─► XLinkOut "depth" ──XLink──►  q_depth maxSize=4 blocking=False
                                                        │
                                                        ▼  q.get()  ← returns OLDEST
                                                   RTMW3D infer (~21 ms)
                                                        ▼
                                                   depth sample + backproject (~9 ms)
                                                        ▼
                                                   P0 smoother ─► P1-1 tracker ─► UDP
```

Audited call sites: `oak_depth.build_rgbd_pipeline` (queue creation),
`wholebody_udp_sender.py:227-228` (host queues), `:283/:290` (drain).

## 2. Root cause — arithmetic-exact

`DataOutputQueue.get()` returns the **OLDEST** queued packet (FIFO). Inference (~21 ms) plus depth
(~9 ms) plus send cannot sustain the 30 fps sensor once a subject is present (measured 21.3 fps), so
the host queue sits **full at maxSize=4**:

> **4 frames × 33.3 ms = 133 ms** — versus the **131.4 ms** measured live in P0 acceptance §4d.

Every pose was therefore computed from a frame ~4 sensor periods old. Nothing was "slow"; the system
was working on stale data.

Two secondary audit findings:

- **`XLinkOut.input` blocking / queue size is never configured** in `build_rgbd_pipeline`, so both keep
  DepthAI's default (blocking, size 8) on the *device* side — a potential second backlog. Measurement
  showed this is **not** contributing (unloaded frame age lands at 14.08 ms, i.e. pure sensor→host
  transfer), so per "smallest correct change" it was left alone.
- **RGB/depth were paired by queue ordinal, not timestamp** (audit F-09). Now quantified for the first
  time: the old pairing was mis-associating depth by **54.56 ms** — about 1.6 frames.

## 3. Baseline measurements

Two conditions, real OAK-D. The loaded condition uses `--inject-load-ms 20` (test-only) to reproduce

live with a subject.**

|---|---|---|---|
| loaded (~18.8 fps) | 18.8 | FIFO | **130.95** / 146.06 / 147.04 / 147.34 ms |
| loaded (~18.7 fps) | 18.7 | latest-frame | **30.71** / 45.77 / 46.88 / 47.71 ms |
| unloaded (~30 fps) | 30.0 | FIFO | **75.00** / 75.43 / 80.85 / 93.19 ms |
| unloaded (~30 fps) | 30.0 | latest-frame | **14.08** / 14.33 / 25.50 / 32.37 ms |

## 4. New queue policy

Smallest correct change, entirely host-side, in the acquisition block:

```
_rgb_pkt   = q_rgb.get()          # one blocking read guarantees liveness
_depth_pkt = q_depth.get()
if latest_frame:
    extra = q_rgb.tryGetAll()     # drain whatever else arrived
    if extra: _rgb_pkt = extra[-1]              # keep only the NEWEST
    cands = [_depth_pkt] + q_depth.tryGetAll()
    _rgb_pkt.getTimestamp() → pick the depth packet CLOSEST in timestamp
```

- Queue size is **unchanged** (`maxSize=4`) — no large buffer was added.
- Historical frames are **discarded, not processed**.
- Toggle: `--latest-frame` (default ON) / `--no-latest-frame` for A/B.

## 5. RGB/depth synchronization — improved, not risked

The brief's concern (newest RGB + oldest depth) is explicitly avoided: depth is chosen by **closest
timestamp** to the selected RGB frame, from the drained candidate set.

| condition | policy | sync median / p95 / max |
|---|---|---|
| loaded | FIFO | 12.15 / 21.18 / **54.53** ms |
| loaded | latest-frame | 12.09 / 12.09 / **12.09** ms |
| unloaded | FIFO | **54.56** / 54.56 / 54.64 ms |
| unloaded | latest-frame | **12.20** / 12.21 / 12.26 ms |

Pairing got **better in every statistic** — up to 4.5× on median and 4.5× on max. The residual ~12.1 ms
is a stable systematic offset (device-side stereo processing lag), not a pairing error: it is identical
at median, p95 and p99.

## 6. Freshness metrics (permanent production diagnostics)

| `frameAgeMs` | host processing time − camera frame timestamp (via `dai.Clock.now()`) |
| `queueDepth` | packets waiting when the frame was sampled |
| `staleDropped` | frames discarded as stale this iteration |
| `rgbDepthSyncMs` | \|RGB timestamp − depth timestamp\| |
| `trackerMs` | P1-1 cost (from P1-1) |

**37/37 unit assertions still pass**. No P0 or Unity code was changed.

**Per-joint jitter on real human motion is NOT yet re-measured** — it needs a subject (§13).

> **Methodological warning for that test:** with latest-frame the effective inter-frame interval is
> larger (frames are skipped), so *per-frame* displacement will legitimately increase without any
> jitter increase. The comparison must be **velocity-normalised** (m/s, using the real timestamps),
> not raw per-frame displacement. Comparing per-frame displacement between the two policies is not
> apples-to-apples.

## 13. Remaining issues

1. **Phases 5–6 need a human subject.** The real-motion A/B (static / walking / fast arms / fast legs /
   dancing) and the per-joint jitter regression are not yet measured. The load simulation reproduces the
   *latency* condition faithfully but cannot reproduce real *motion*.
   Command: `run_p12_ab.bat` (below).
2. **Rare compute spikes** with latest-frame: 0.3–0.7% of frames show host→pose > 80 ms (max 111–116 ms)
   versus 0% on FIFO. Cause not established — plausibly the `tryGetAll` drain coinciding with a slow
   inference or GC. Low incidence, but it should be watched, not dismissed.
3. **Device-side `XLinkOut` queues remain at DepthAI defaults** (blocking, size 8). Measurement says
   they are not contributing today; if a future slower host shows frame age above sensor transfer plus
   one frame, set `input.setBlocking(False)` / `setQueueSize(1)` there too.
4. **~12.1 ms RGB/depth offset is systematic** (device stereo lag). Not corrected — correcting it would
   mean changing the depth pipeline, which this task must not do.
5. `--inject-load-ms` is a **test-only** instrument and must never be set in production.
